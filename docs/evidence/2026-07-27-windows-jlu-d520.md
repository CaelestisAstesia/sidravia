# Windows / 吉林大学 D520 Alpha 现场证据

## 结论

提交 `508197dc3034c78e702630d2910d7f53df55eba6` 构建的 Windows amd64 CLI 和 daemon
在一台真实 Windows 11 机器上完成了吉林大学 Dr.COM 5.2.0(D) 的认证、七轮保活、
停止、Logout 和 daemon 清理。

这份证据只证明该提交、该机器、该校园网络和该次现场条件。它不代表其他学校、其他
Dr.COM 变体、所有 Windows 网络拓扑或所有官方客户端报文长度已经得到验证。

## 人类执行入口

现场使用以下公开命令形状：

```powershell
.\sidravia.exe status
.\sidravia.exe auth start --profile jlu --username '<redacted>'
.\sidravia.exe auth status session-1
.\sidravia.exe auth stop session-1
```

密码通过 Windows 交互式隐藏提示输入。daemon status 返回 build `508197d`，Session
选择预期物理网卡并进入 `authenticated`。

## 脱敏线级时间线

下表中的长度是本次观察值，不是固定长度白名单。客户端继续按协议结构生成请求；服务端
响应按所需字段的结构最小长度和 4096 字节上界验证，额外字节保持不透明。

| 阶段 | 客户端观察 | 服务端观察 |
| --- | --- | --- |
| Challenge | 20 B | 76 B |
| Login | 330 B | 45 B success |
| KA1 bootstrap | 42 B | 72 B |
| 首次 KA2 Type 1 | 40 B，serial `00` | 272 B，特殊 `10 01 0b` Type 6 |
| 第二次 KA2 Type 1 | 40 B，serial `01` | 40 B，普通 Type 2 |
| bootstrap KA2 Type 3 | 40 B，serial `02` | 40 B，普通 Type 4 |
| 后续 heartbeat | 每轮 KA1 + KA2 `1-3` | 对应 KA1 + Type 2/4 |
| Logout 前 Challenge | 20 B | 76 B |
| Logout | 80 B | 25 B ACK |

bootstrap 在不到一毫秒的本地时间窗内完成，随后观察到七轮约 20 秒间隔的 heartbeat。
Session 在约 133 秒后接受 Stop。

没有公开任何 Tail 内容。仅比较字段相等关系，结果为：

- 首个 bootstrap 请求 Tail 为零；
- 特殊 Type 6 后第二个 Type 1 继续使用原 Tail；
- 普通 Type 2 的 refill 被下一次 Type 3 使用；
- 普通 Type 4 的 refill 被第一轮 heartbeat Type 1 使用。

Stop 后客户端发出 fresh Challenge，再发送一次 Logout 并收到 ACK。该 UDP stream 随即
结束，没有继续发送 KA1/KA2。Session 保持 `suspended`。

## Windows 生命周期

- CLI 与前台 daemon 的 loopback IPC 正常。
- 多次 `auth status` 在七轮 heartbeat 期间持续返回 `authenticated`。
- `auth stop` 返回 `suspended`，后续查询保持该状态。
- daemon 接受 `Ctrl+C` 后正常退出。
- `%LOCALAPPDATA%\Sidravia\runtime.json` 在退出后不存在。

## 抓包边界

原始抓包只保存在 ignored 私有证据边界，不进入 GitHub。其 SHA-256 为：

```text
f55bd7896c307c6c7180c2f159a4824ecafd33de274643975cebbe4568a2492b
```

抓包关闭前又启动了官方客户端。它使用不同源端口和独立 UDP stream，因此与 Sidravia
时间线可以确定性分离；物理网卡和 Clash TUN 上的重复观察也分别标识。该官方客户端
再次产生一个 346 字节 Login 样本。这只能增加一个样本，不能证明 346 是固定长度，也
不能证明相对 Sidravia 的扩展恒定为 16 字节。
